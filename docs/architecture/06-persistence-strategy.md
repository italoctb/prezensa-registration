# Persistência de Registration

Esta é a fonte canônica para os adapters, garantias de armazenamento e consistência entre `RegistrationDraft` e `Registration`. O [modelo e suas regras](04-domain-model.md) ficam no documento de domínio; a [árvore física](08-local-development.md) fica no guia do workspace.

## Stores e adapters atuais

`MongoRegistrationDraftRepository` persiste o Draft parcial na coleção `registration_drafts`. Cada documento guarda ID, owner, status, valores preenchidos, timestamps UTC como ticks, `RegistrationId` opcional e `Version`. A reconstituição passa por `RegistrationDraft.Restore`, que valida o estado e não reemite eventos de criação. Um índice único parcial em `ownerId` para `status = InProgress` garante no máximo um Draft ativo por owner, inclusive quando dois `StartDraft` competem. `AddOrGetActiveAsync` devolve o vencedor da corrida. `UpdateAsync` substitui o documento somente se `_id` e versão anterior coincidirem; divergência produz `ConcurrencyConflict`. O índice é criado na primeira inserção pelo adapter.

`OracleRegistrationRepository` persiste Registration formal em `REGISTRATIONS`. O script embutido [`001_registrations.sql`](../../services/registration/src/Registration.Infrastructure/Persistence/Oracle/Sql/001_registrations.sql) é a definição canônica da tabela neste checkpoint. `OracleRegistrationSchemaInitializer.EnsureCreatedAsync` cria a tabela se ela ainda não existir; o host `Registration.Api` o chama no startup antes de atender escrita. Ele **não** altera esquemas existentes: evolução de schema e migrações versionadas serão necessárias antes de produção. O perfil imutável fica em `APPLICANT_JSON` (CLOB); CPF também fica em coluna própria para consulta e unicidade. IDs de origem e Registration têm constraints únicas. Status, dados de aprovação, falha, timestamps e versão são colunas separadas, com checks para as principais consistências. Timestamps são ticks UTC de `DateTimeOffset`; não há atributos de ORM no Domain. O adapter possui leitura e atualização com comparação de versão para evolução futura do ciclo de Registration.

O check `ExistsByCpfAsync` no submit permite erro antecipado, mas a constraint `UX_REGISTRATIONS_CPF` é a garantia autoritativa contra corrida. `AddForDraftAsync` traduz a violação dessa constraint para `CpfAlreadyRegistered`. A constraint de `SOURCE_DRAFT_ID` permite recuperar o mesmo Registration em retries, desde que o perfil do Draft seja igual ao já gravado. Uma diferença gera `ConcurrencyConflict`, em vez de associar silenciosamente dados divergentes.

`ViaCepPostalCodeLookup` implementa o port neutro `IPostalCodeLookup` por HTTP. CEP estrutural é validado pelo value object; o adapter converte logradouro, bairro, cidade e UF para valores locais. `erro: true` ou resposta incompleta significa CEP não encontrado. Falha HTTP permanece falha técnica. `AddressNumber` e complemento continuam dados fornecidos pelo usuário; o provider não autentica a existência ou titularidade de um endereço.

O acesso local guarda contas em `registration_accounts` com e-mail canônico como `_id` único e `OwnerId` estável. `registration_email_codes` guarda somente HMAC do código, finalidade, expiração, contagem de falhas e versão; a troca de desafio usa comparação de versão, e consumo/contagem de erro são operações atômicas. `registration_sessions` guarda somente hash do token opaco, owner e expiração; revogação remove a sessão. Índices TTL removem desafios e sessões expirados eventualmente, mas expiração é sempre verificada na consulta. O e-mail é enviado depois de gravar o desafio; se o transporte falha, o desafio é invalidado para permitir novo pedido. Não há transação entre Mongo e SMTP: entrega incerta ou falha de resposta ainda pode exigir novo pedido. Consumo do código, inserção da conta e criação da sessão também não formam uma transação única: se uma escrita falhar após o consumo, o usuário precisará pedir outro código; se a conta existir e a sessão falhar, poderá usar o fluxo de login. Essa recuperação deve ser validada operacionalmente antes de produção. O [fluxo de autenticação](09-registration-api.md) é documentado no contrato HTTP.

## Composição e configuração

`services.AddInfrastructure(configuration)` registra os repositories de Draft, Registration e acesso, `OracleRegistrationSchemaInitializer`, o HTTP client de CEP e o transporte SMTP. Exige MongoDB, Oracle e configuração SMTP; a chave HMAC é lida pelo host. Nenhuma senha fica no repositório. A Application define os ports e não referencia drivers; Infrastructure referencia Application e Domain. `Registration.Api` usa essa composição; configuração e rotas estão no [contrato HTTP](09-registration-api.md). Ainda não há container nem Compose.

## Submit entre Mongo e Oracle

O fluxo atual grava Registration no Oracle e depois marca o Draft como Submitted no Mongo. Não há transação atômica entre os bancos. Se o Oracle confirmar e o Mongo falhar, um retry do submit carrega o Draft, localiza Registration por `SOURCE_DRAFT_ID`, compara o perfil completo e tenta novamente `MarkSubmitted` com o mesmo ID. A comparação de versão no Mongo impede sobrescrever uma atualização concorrente. Se o Draft mudou após a primeira gravação, o retry retorna `ConcurrencyConflict` e requer reconciliação operacional; nenhuma segunda Registration é criada. A API traduz esse conflito para HTTP `409`.

Isso cobre o retry comum, mas não fornece atomicidade entre stores nem recuperação automática de todos os estados divergentes. Uma rotina de reconciliação e sua política de operação, além de testes executados com os dois bancos, são decisões necessárias antes de produção. Não foi introduzida transação distribuída, Saga, Outbox ou Kafka por causa desse problema. Domain events continuam internos e não são publicados pelo adapter.

O registration-service poderá consultar seus próprios dados. Um Query Service separado depende de necessidade real de projeção entre contextos; o storage dele não foi decidido. Fraud escolherá sua própria persistência. Redis continua fora: poderá servir cache, lock, limite de taxa ou estado efêmero se houver requisito concreto, mas não substitui constraints ou dados duráveis.
